# M4.2 — proposed synthetic receipt scope

Status: **owner approved all three decisions and M4.2 implementation on 2026-10-23**.
Execution contract: [Issue #29](https://github.com/porntaned/ERP-for-Factory/issues/29),
[assignment](../assignments/issue-29-stock-receipt.md). Delivery/acceptance is tracked
there; approval of this scope does not mean implementation is complete.
The proposal below was prepared against M4.1 `a8c93fc`; implementation uses merged
documentation baseline `21ab14082fb18a99bfa1fb1c3a5061323bfadc33`.

## Smallest useful delivery

An internal Inventory receipt command for one existing saved Lot and one Warehouse
in the same Organization. Receive a positive exact quantity in the Item's base UOM
using M4.1's precision/range rules. Reuse existing Lot identity rather than add
supplier, purchasing, Item classification, UOM conversion or new Lot creation.
All examples and test data are synthetic.

Atomically persist a typed receipt record linked one-to-one to its immutable
positive ledger entry, retaining actor, reason, request identity and database time.
This makes receipt intent auditable without treating every positive delta as a
receipt. A failed command or outer rollback must leave neither record nor delta.
The exact minimal schema/API would be locked in the approved Issue before RED tests.

## Decisions approved by the owner

1. **Receipt authority:** require a persisted active User with the exact `WAREHOUSE`
   role at the destination Warehouse. No implicit superuser, `APPROVER`, `QUALITY`
   or `PRODUCTION` bypass. Recheck/lock persisted User and grant in the transaction;
   cached instances and an earlier policy result are insufficient.
2. **Quality boundary:** allow physical receipt into HOLD stock, including a pair
   with no disposition (existing default HOLD). Preserve the current disposition;
   receiving must never auto-release or fabricate a Quality decision. A receipt
   into an already RELEASED pair preserves RELEASED under this minimal existing-Lot
   proposal. If each delivery needs fresh inspection, it requires a separate Lot or
   an approved delivery-level Quality contract before implementation. Coordinate
   checks and append under the shared Lot lock, with a lock order reviewed against
   ledger triggers and Quality transitions. Transfer/issue eligibility comes later.
3. **Retry boundary:** include a required UUID request key for this receipt command
   so a retry cannot double-receive. Identical authorized retries return the same
   receipt; changed payload conflicts; concurrent identical keys produce one receipt
   and one delta. This is a narrow proposed overlap with M4.4, requiring explicit
   scope acceptance; M4.4 remains open for broader movement/concurrency guarantees.

The owner selected these three decisions, including HOLD receipt and receipt-only
idempotency. Any later policy change needs a separate reviewed contract; these
choices were not established by M4.1's storage invariants.

## Dependencies and acceptance criteria

Dependencies: merged Item/UOM, Lot, facilities and Warehouse roles; Quality's
warehouse-scoped HOLD/RELEASED history; M4.1 ledger. Existing seams are
[`inventory/services.py`](../../inventory/services.py),
[`access_control/policies.py`](../../access_control/policies.py),
[`access_control/models.py`](../../access_control/models.py) and
[`quality/services.py`](../../quality/services.py). These currently supply a balance
snapshot, role policies and Quality transitions, not a receipt command.

The approved Issue/assignment above fixes these decisions and allowed files.
Acceptance criteria:

- Authorized receipt of 100 creates one typed receipt/ledger pair and balance 100;
  a later independent receipt adds exactly its quantity and retains both histories.
- Reject unsaved/manual-PK, missing or cross-Organization parents; inactive/stale or
  unsaved actors; wrong/revoked Warehouse grants; invalid/zero/negative/non-finite,
  excess-precision and out-of-range quantity; blank reason or invalid request key.
- Check HOLD/default HOLD/RELEASED behavior under the approved policy, with no
  unauthorized Quality event or change to existing Quality transition behavior.
- Prove all-or-nothing rollback, immutable receipt-to-ledger linkage and the approved
  retry/conflict behavior on PostgreSQL 18.6. Observe actual lock contention for
  authorization revocation/deactivation, Quality transitions and concurrent receipts;
  do not substitute mocks or timing-only assertions for concurrency evidence.
- Record controlled PostgreSQL RED/GREEN, fresh migration/drift checks, targeted and
  relevant/full regressions, exact tested SHAs and commands, independent Scrutinize
  and a PR for owner review. Stop before merge/deploy.

Excluded: M4.3 transfers, generic movement framework, full M4.4 completion, M4.5
reversals, M4.6 UI/API endpoints/admin actions, M4.7 demo, adjustments, valuation,
real stock/data, full inspection, privileged access, Manufacturing, deployment and
new significant dependencies. This proposal does not change milestone completion.
